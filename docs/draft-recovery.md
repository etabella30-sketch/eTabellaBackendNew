# Full Fact draft recovery (limited scope)

The recovery API supports only new Full Fact drafts whose captured content belongs to one PDF or transcript source. It does not authorize or restore edited Facts or cross-document links. A client must validate current issue/recipient options after reauthentication and refuse this flow for unsupported drafts. Draft text stays encrypted in the user's browser; the service stores an AES-GCM-wrapped random data key for at most one hour, not plaintext draft or plaintext data keys.

Before enabling the client, configure `DRAFT_RECOVERY_MASTER_KEY` on every coreapi replica with the same dedicated, securely generated 32-byte key encoded as canonical base64. Keep it in the deployment secret manager and out of source control, logs and browser bundles. Missing or malformed configuration makes the API return unavailable. Rotating the key invalidates all pending drafts. Coreapi and authapi must use the same Redis instance: authapi atomically invalidates the user recovery epoch while ending the verified session at signout. Deploy both services and test session/Redis failover before enabling the client. Redis TTL and epoch checks fail closed on errors; explicit signout cannot complete if this atomic step is unavailable.

Recovery keys use a Redis hash tag containing the complete existing `user/<userId>` session key. This places the session, epoch, rate limit and draft records in the same Redis Cluster hash slot, allowing their atomic scripts to run without `CROSSSLOT`. The application still needs a client and deployment configured for its actual Redis topology; key colocation alone does not configure Redis Cluster routing or high availability. No automatic migration is provided for recovery records written by pre-release builds with older key names; these short-lived test records expire.

The PDF access policy intentionally reuses Case Activity's stricter document-visibility subset. It may deny documents available through other Reader access paths. Transcript recovery requires an existing, undeleted session in the requested case plus active case membership or global-admin status. Both issue and release recheck access. No positive permission result is cached. The source ID in the request is not an access grant, and the authenticated JWT subject is the only user identity used.

The existing client may call signout after some service-specific 401 responses even if the auth token is still valid. In that case explicit signout invalidates pending keys and the draft cannot be recovered; true token expiry is rejected by the auth middleware and does not increment the epoch. A client must tell the user when recovery could not be prepared or restored; this is not a guarantee for changes that were not durably encrypted before network loss.

New sign-ins contain a random JWT ID; Redis holds a SHA-256 digest of the current token, not the token itself. Updated global and Realtime HTTP middleware atomically delete a session for an expired token only if its browser and digest are still current. Legacy sessions without a digest continue to authenticate as before, but their expired tokens cannot delete a Redis session. Every deployed host bundling `JwtMiddleware` and the Realtime server must receive the updated middleware before relying on the late-401 race fix. Recovery and explicit signout check the current digest; other ordinary-token validation paths retain their previous browser-ID semantics. A stale signout that is rejected does not clear the cookie, but a successful signout response delayed until after a later login could still clear the new cookie. This race requires a separate cookie/session protocol change and remains unresolved. An offline signout cannot update the server epoch; client-side encrypted-envelope cleanup is therefore required and cannot substitute for a server-side revocation guarantee.
